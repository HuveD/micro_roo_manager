# 통합 개발 규칙 가이드라인

## 핵심 원칙

### 언어 규칙
- 모든 응답과 문서는 한국어로 작성
- 기술 용어는 필요시 영어 병기 가능

### 개발 철학
- **속도와 품질의 균형**: 빠른 개발 속도 유지, 품질 타협 불가
- **자동화 우선**: 반복 작업은 즉시 자동화
- **명확성 추구**: 코드는 자체 문서화
- **실용주의**: 과도한 추상화보다 실용적 해결책 선호

## 코드 품질 규칙

### 메서드 및 파일 설계
- **메서드 크기**: 15줄 이하 유지
- **파일 크기**: 500라인 미만으로 관리 (초과 시 분할 검토)
- **단일 책임 원칙(SRP)**: 메서드, 클래스, 파일 모두 하나의 역할만 수행
  - 파일이 500라인을 초과하면 단일 책임 원칙 위반 가능성 검토 (문서 파일은 검토 제외)
  - 책임별로 파일 분리 (예: UserService → UserCreator, UserValidator, UserUpdater)
- **명확한 입출력 정의**: 메서드 시그니처만으로 역할 파악 가능

### 타입 안전성
- `any`, `unknown` 사용 금지 (예외: 외부 API 통합 초기, 레거시 마이그레이션)
- 명확한 인터페이스 정의 필수

### 조건부 로직 최소화
- Strategy Pattern 활용으로 복잡한 조건문 제거
- Guard Clause 적극 사용
- Tell, Don't Ask 원칙 준수

## 실용적 테스트 전략 (Pragmatic TDD)

### 테스트 ROI 평가 기준
```
테스트 가치 = (복잡도 × 비즈니스 중요도) / 유지보수 비용
```

### 필수 TDD 적용 (높은 ROI)
**✅ 핵심 비즈니스 로직:**
- 가격 계산, 할인 로직
- 사용자 권한 검증
- 결제 처리 흐름

**✅ 복잡한 알고리즘:**
- 데이터 변환 로직
- 검색/필터링 알고리즘
- 상태 기계

**✅ 외부 통합:**
- API 클라이언트 (반드시 Mock)
- 외부 서비스 연동

### 테스트 제외 (낮은 ROI)
**❌ 단순 로직:**
- getter/setter
- 단순 CRUD 연산
- DTO 매핑

**❌ UI/프레임워크 코드:**
- 컨트롤러 라우팅
- 뷰 렌더링
- 프레임워크 기본 기능

### 테스트 수준 가이드
- 핵심 로직: 단위 테스트 + 통합 테스트
- 보통 로직: 통합 테스트만
- 단순 로직: 테스트 생략

### ⚠️ 테스트 케이스 검증 제외 (반드시 Mock/Stub 사용)
- **실제 API 요청**: 외부 서비스 호출, HTTP 요청
- **DB 연산**: 실제 데이터베이스 CRUD 작업
- **파일 시스템 접근**: 실제 파일 읽기/쓰기
- **시간 함수**: Date.now(), setTimeout 등

**대체 방안**: 
- Mock/Stub/Test Double 활용
- In-memory DB 또는 Test Container
- Virtual File System
- jest.spyOn() 또는 sinon.stub()

## MCP 도구 활용

### 역량 중심 접근
- 기술 문서 필요 → `context7`
- 최신 정보 필요 → `perplexity`
- 웹페이지 내용 필요 → `firecrawl`

### 실패 시 대체 전략
- MCP 도구 실패 → 내부 지식 활용 + 한계 고지
- 부분 정보 획득 → 획득 정보로 최선 답변
- 완전 실패 → 대체 접근 방법 제시

## 개발 워크플로우

### 기본 흐름
1. **요구사항 분석** → 비즈니스 목표 명확화, 제약사항 식별
2. **테스트 필요성 평가** → ROI 기반 TDD 적용 여부 결정
3. **개발 접근**
   - TDD 적용: Red → Green → Refactor
   - 직접 구현: 코드 작성 → 필요 시 테스트 추가
4. **품질 검증** → 테스트 통과, 코드 품질 규칙 준수
5. **문서화** → 코드 변경 시 문서 동시 업데이트

### 커밋 전 체크리스트
- [ ] 필요한 테스트 통과 (핵심 로직만)
- [ ] 코드 품질 규칙 준수
- [ ] 불필요한 파일 제거
- [ ] 의미 있는 커밋 메시지
