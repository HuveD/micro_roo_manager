# 통합 개발 규칙 가이드라인

## 핵심 원칙

### 언어 규칙
- 모든 응답과 문서는 한국어로 작성
- 기술 용어는 필요시 영어 병기 가능

### 개발 철학
- **속도와 품질의 균형**: 빠른 개발 속도 유지, 품질 타협 불가
- **자동화 우선**: 반복 작업은 즉시 자동화
- **명확성 추구**: 코드는 자체 문서화
- **실용주의**: 과도한 추상화보다 실용적 해결책 선호

## 코드 품질 규칙

### 메서드 및 파일 설계
- **메서드 크기**: 10줄 이하 유지
- **파일 크기**: 500라인 미만으로 관리 (초과 시 분할 검토)
- **단일 책임 원칙(SRP)**: 메서드, 클래스, 파일 모두 하나의 역할만 수행
  - 파일이 500라인을 초과하면 단일 책임 원칙 위반 가능성 검토
  - 책임별로 파일 분리 (예: UserService → UserCreator, UserValidator, UserUpdater)
- **명확한 입출력 정의**: 메서드 시그니처만으로 역할 파악 가능

### 타입 안전성
- `any`, `unknown` 사용 금지 (예외: 외부 API 통합 초기, 레거시 마이그레이션)
- 명확한 인터페이스 정의 필수

### 조건부 로직 최소화
- Strategy Pattern 활용으로 복잡한 조건문 제거
- Guard Clause 적극 사용
- Tell, Don't Ask 원칙 준수

## 테스트 전략 (FastTDD)

### 테스트 피라미드
- Unit Tests: 70% (격리된 단위 테스트)
- Integration: 25% (모듈 간 상호작용)
- E2E: 5% (중요 사용자 경로만)

### 테스트 작성 기준
**✅ 반드시 테스트:**
- 핵심 비즈니스 로직
- 복잡한 알고리즘
- 에러 처리 로직
- 공개 API 인터페이스

**❌ 테스트 불필요:**
- 게터/세터, 단순 위임 메서드
- 프레임워크 기능, UI 스타일링

### ⚠️ 테스트 케이스 검증 제외 대상
- **실제 API 요청**: 외부 서비스 호출, HTTP 요청
- **DB 연산**: 실제 데이터베이스 CRUD 작업
- **파일 시스템 접근**: 실제 파일 읽기/쓰기

**대체 방안**: Mock, Stub, Test Double 활용하여 격리된 테스트환경에서 검증

## MCP 도구 활용

### 역량 중심 접근
- 기술 문서 필요 → `context7`
- 최신 정보 필요 → `perplexity`
- 웹페이지 내용 필요 → `firecrawl`

### 실패 시 대체 전략
- MCP 도구 실패 → 내부 지식 활용 + 한계 고지
- 부분 정보 획득 → 획득 정보로 최선 답변
- 완전 실패 → 대체 접근 방법 제시

## 개발 워크플로우

### 기본 흐름
1. **요구사항 분석** → 비즈니스 목표 명확화, 제약사항 식별
2. **TDD 사이클** → Red(실패테스트) → Green(최소구현) → Refactor(품질개선)
3. **품질 검증** → 테스트 통과, 코드 품질 규칙 준수
4. **문서화** → 코드 변경 시 문서 동시 업데이트

### 커밋 전 체크리스트
- [ ] 모든 테스트 통과
- [ ] 코드 품질 규칙 준수
- [ ] 불필요한 파일 제거
- [ ] 의미 있는 커밋 메시지

## 파일 및 문서 관리

### 기본 원칙
- 명명 규칙: `snake_case`
- 중복 제거: 같은 내용은 하나의 문서로 통합
- 버전 관리: 구식 문서 즉시 삭제

### Mermaid 다이어그램 규칙
- 노드 ID는 영숫자와 언더스코어만 사용
- 특수문자 포함 텍스트는 큰따옴표로 감싸기
- 주석(`%%`) 사용 금지
